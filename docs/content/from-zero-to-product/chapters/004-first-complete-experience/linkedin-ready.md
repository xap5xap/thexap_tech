A small first increment still needs a complete user path.

"Build the request form" leaves an important question open: what can the person actually observe after pressing Save?

Try writing one outcome sentence before dividing the work:

When [role] performs [action] in [starting state], they can observe [result], under [named conditions].

Then trace that action through the interface, service and data, back to the visible result. Include an external surface only when the promise needs it.

In a fictional request tracker, the finish is one stored request visible in the list, including after reload.

Now choose a failure. If the response disappears after storage, the browser cannot honestly say "Saved." Recovery needs to reconcile the same attempt, preserve the input and avoid a duplicate.

Give setup, integration, checks and cleanup an owner too. Those are part of delivering the increment.

A demonstration can establish that named path under named conditions. Keep the remaining release obligations explicit.
