Seven accepted items can still leave your original six-item plan unfinished.

In a fictional sprint, a team accepts five original items and two additions. One original obligation remains open. Reporting only "7 done" hides both the scope change and the unfinished result.

A useful retrospective keeps those distinctions visible:

1. Compare the preserved plan with the demonstrated outcome. Label added scope and changed acceptance conditions.
2. Separate elapsed time from recorded waits and actual effort. A 24-hour interval with four waiting hours does not establish 20 coding hours.
3. Pick one process experiment with an owner, a later check and a reason to keep, revise or retire it.

If you update an agent skill to prepare dependencies before launch, that proves the instructions changed. Later runs must show whether avoidable pauses changed too.

Keep the first record small: intended outcome, actual evidence, one friction, one change and the next check.

The guide includes a worked sprint example and an improvement experiment you can adapt.
